## 学习内容

### 一、MCP 四大要素的正确关系

纠正了之前对四个关系的错误理解：

**错误模型：** LLM → CLI → MCP Server → Tool Schema + Permission

**正确模型：**

```
你 ↔ Hermes CLI（整车，内含 LLM + MCP Client + 工具系统）
                             ↓
                       MCP Server（独立进程）
                            ├── Tool Schema（声明）
                            └── Tool 实现（执行）
```

关键纠正：
- **LLM 不是外面调 CLI，LLM 就是 CLI 的一部分**——CLI 是整车，LLM 是引擎
- **MCP Client 在 Hermes 内部**，负责：启动时发现工具、调用时转发请求、权限拦截
- **Permission 在 MCP Client 层，不在 Server 里**——Server 只管干活，不管谁在调
- 用 Java 类比：MCP Client = Controller + AOP 拦截器，MCP Server = 微服务，Tool Schema = Swagger 文档

### 二、CLI 到底是什么

Hermes CLI = 一个终端程序，像 git/docker/npm 一样，但功能是"连接 LLM + 执行操作"。

内部组件：
- **TUI**（终端界面）
- **LLM 客户端**（连接 DeepSeek API）
- **内置工具系统**（read_file / terminal / search_files 等）
- **MCP Client**（连接外部 MCP Server）
- **Skill 系统**（按场景加载操作手册）
- **配置管理**（模型、API key、streaming）

**不是"商品"，是成熟的开源生产力工具。**

### 三、MCP 本质总结

**MCP = 一个协议，让 LLM 能调用不同语言、不同平台的服务。**

| 解决的问题 | 方案 |
|-----------|------|
| LLM 只能聊天不能操作外部系统 | 统一协议包装外部能力为 Tool |
| 每个工具要单独适配 | 统一规范，Java/Python/Go/Node.js 都按同一套接 |
| 平台绑定 | 写一次，Hermes/Claude Code/VS Code 都能用 |

### 四、传统应用 vs Hermes CLI 的本质区别

| | 传统应用 | Hermes CLI |
|--|---------|-----------|
| 功能边界 | 固定，写死在代码里 | 动态，由 LLM 实时编排 |
| 功能组合 | 开发阶段组合好 | 对话阶段实时组合 |
| 返回内容 | 数据（JSON/DTO） | 答案（经分析理解后的结果） |

根本区别：传统应用是"预制的"，Hermes CLI 是"即时的"。

### 五、JavaCliTool 包装成 MCP Server 的思路

去掉 LLM 部分，把 HandbookClient / Tool 包装成 MCP 协议的 Tool，打包成可执行 JAR。
Hermes 配置一行 `mcp_servers.javacli-tool: { command: "java", args: ["-jar", "..."] }` 即可自动发现和调用。

### 六、关于第一性原理：接口约束的局限性

类比 2019 年关于 JDBC 接口 vs 事务日志的讨论（https://x.com/allenholub/status/1200393155273826304）：
- 接口（Tool Schema）只规定"怎么调"，不保证"调得安全"
- Permission 层做统一拦截（能不能用 Tool）
- Server 实现层做细粒度权限（能操作哪些数据）
- 审计/隔离/限流需要额外处理，协议层不管

### 七、一句话金句

> **MCP 的核心价值不是"LLM 能调用更多东西"，而是"用一种统一的方式，让所有 MCP 客户端都能自动发现和使用你的工具"。写一次，到处跑。**
