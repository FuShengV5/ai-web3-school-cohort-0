### 学习内容

- **Handbook 章节**：Evaluation（评估）

- **关键概念**：

  传统测试 vs LLM Evaluation：
  - 传统测试：输入X → 输出Y，确定性判断对错
  - LLM Evaluation：概率性输出，从多个维度打分，类似"面试实习生"
  - 可保留的传统测试部分：接口调通、功能测试、压测（应用层不挂掉）
  - 需要重新定义的部分：测试用例（用户问题无法穷举）、正确性判断（不是二选一）

  Evaluation 的几个核心维度：
  - **Accuracy（准确性）** — 数据对不对
  - **Helpfulness（有用性）** — 用户体验、完整度
  - **Safety（安全性/无害性）** — LLM 不教人做危险事
  - **Honesty（诚实性）** — 不知道就说不知道，不编造
  - **Conciseness（简洁性）** — 不长篇大论
  - **Language Consistency（语言匹配）** — 按用户语言回答
  - **Attribution（可追溯性）** — 回答可追溯到原始文档

  评估方法：
  - **LLM-as-a-Judge** — 用 LLM 给 LLM 打分
  - **Multi-model Ensemble** — 多个 LLM 交叉验证，投票取多数
  - **Checklist-based** — 把评分标准细化为检查清单（是非题），比模糊打分更可靠

  评估标准的优化飞轮：
  ```
  定义检查清单 → LLM 批量评估 → 人工抽检漏网之鱼
  → 提炼新检查项 → 继续评估（持续优化）
  ```

  RAGAS 基础维度框架：
  - 底层：Harmlessness / Honesty / Helpfulness
  - RAG 场景：Faithfulness / Answer Relevancy / Context Precision / Context Recall
  - 类比 Java：基础维度 = interface，业务维度 = implements

  数据源限定边界的工程方案：
  - RAG 检索不到内容 → 代码层直接返回"无法回答"，不让 LLM 参与
  - 本质是 code-constraint：用代码做路由拦截，LLM 只处理知识库范围内的问题
  - 类似 Java CLI Tool 中路径预校验的做法：先代码验一把，通过才轮到 LLM

- **代码 / 实验**：无

### 问题与卡点

- LLM Evaluation 不能像传统测试一样写死输入输出，需要多维度的评价体系
