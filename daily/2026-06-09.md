### 学习内容

- **Handbook 章节**：ai/inference（推理服务）—— Phase 1 AI 收尾章

- **关键概念**：
  - Inference ≠ 调 API，而是**模型从收到请求到返回结果之间所有工程决策的总和**
  - API Model：调云端模型，不是"没工程问题"——要管超时、重试、速率限制、成本、日志脱敏
  - Local Model：私有环境部署——数据不出内网、版本可控，但硬件贵、运维复杂（你已用的伏羲 Qwen 32B 属于此类）
  - Quantization：质量换空间——FP16→INT8→INT4，显存需求减半到 1/4，质量有损但可接受
  - Serving：把模型变成稳定服务——并发、队列、灰度、监控、降级、日志脱敏
  - 灰度不是随机 10%，是按规则（用户 ID 哈希/内外部）选 10%，保证同一用户体验一致
  - 接口封装层（AiChatService interface）是生产级调用的基础——封装后才谈得上 fallback 和灰度

- **多 Agent 编排思路讨论**：
  - 编排器 = 工作流引擎，控制 CC→Codex→CC→Human 的调用顺序
  - LLM 不直接对话，编排器中转
  - 硬标准（编译/测试）由编排器代码判断；软标准（逻辑完整性）由 Prompt 给定尺子让 CC 判断
  - FAIL/PASS/WARN 三层判定：FAIL=不改交不了差，WARN=功能正确不完美，PASS=放行

- **代码 / 实验**：无新代码，讨论了 SpringAIDemo 下一阶段改进方向：AiChatService 接口封装 + 调用日志 + 结构化异常

### 问题与卡点

- 用不同底模做 LLM 协同（CC 用 Claude，Codex 用 DeepSeek/OpenAI）能减少"串通"风险，但实际中如何实现 token 成本控制还需实践验证
- 速率限制的正确思路：小项目要对用户做频率限制（防滥用），而不是限自己的请求节奏
