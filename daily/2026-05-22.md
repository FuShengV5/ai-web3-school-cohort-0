## 学习内容

### 一、Embedding（嵌入）

**核心：把文字变成数学向量，让语义相近的词在数学上也相近。**

- 计算机不认识文字，字节编码无法表达语义关系
- Embedding 将每个词映射到一个高维空间中的向量（几百到几千维）
- 语义相近的词（"苹果"水果 vs "香蕉"）向量距离近
- 语义不同的词（"苹果"水果 vs "苹果"品牌）向量距离远
- 用余弦相似度（cosine similarity）衡量两个向量的接近程度

**Java 类比：** 字节编码无法区分"苹果（水果）"和"苹果（品牌）"，但 Embedding 向量可以——前者靠近"甜味"轴，后者靠近"科技感"轴。

### 二、Transformer 与 Attention（注意力机制）

**核心：让模型理解句子中每个词和其他词的关系。**

- Self-Attention：处理每个词时，计算它和句子里所有其他词的关联权重
- 权重越高，该词对当前词的"语义贡献"越大
- 多层 Attention 叠加（几十到上百层）逐层建立更复杂的关系理解
- 第一层理解简单关系（"猫追老鼠"），后面层次理解全局语境

**层数关系：** Embedding 是进入 Transformer 前的准备工作。文字 → Embedding 向量 → Attention 层逐层处理 → 输出语义理解。

### 三、Context Window（上下文窗口）

**核心：模型一次能"看到"的最大文本长度，用 tokens 衡量。是硬件限制（GPU 显存）。**

| 概念 | 管什么 | 谁来约束 | Java 类比 |
|------|--------|----------|-----------|
| Context Window | 最大能看多少 token | LLM 硬件（GPU 显存） | JVM 堆内存上限 |
| Prompt | 应该怎么回答 | 你写的人话 | 接口文档/规范 |
| Context Engineering | 拼什么数据给 LLM 看 | 你的框架代码 | 拦截器/过滤器/管道 |

### 四、Context Engineering（上下文工程）

**核心：在有限的窗口里，设计给模型看什么内容、以什么顺序、怎么放，来得到最好的回答。不是约束 LLM，而是约束输入的数据。**

关键策略：
1. **信息优先级排序** — 必须放（系统提示）> 高优先级（RAG 结果）> 次优先（历史摘要）
2. **摘要压缩** — 长对话不做简单丢弃，而是先摘要再放
3. **窗口位置效应** — 开头和结尾模型记忆最好，系统提示和当前问题放两端
4. **窗口余量管理** — 像缓存策略一样精确计算剩余 token，精挑细选放什么

**关键认知：Context Engineering 不是约束 LLM 怎么回答，而是约束你给 LLM 看什么数据。** LLM 本身你约束不了，只能通过给它看什么数据来间接影响它的回答。

### 五、RAG（检索增强生成）

**全称：Retrieval-Augmented Generation**

**一句话：先查资料，再回答。** 就像面试时先翻文档再照着念。

RAG = 外部知识检索 → 拼入上下文 → LLM 基于资料生成

**RAG 和 Context Engineering 的关系：** RAG 是 Context Engineering 里的一种具体数据来源策略——当需要外部知识时，RAG 负责"去外部搜什么东西回来"，然后在 Context Engineering 阶段整合进窗口。

### 六、Chunking（分块）

**核心：把长文档切成语义完整的片段（chunk），每个片段带 metadata（元数据）。**

**切太小的问题：** 语义断裂，"池实现具有高性能和"——模型看不懂。
**切太大的问题：** 噪声多，一个 chunk 混了多个主题的内容，还占窗口。

**好的 Chunking 策略：**
1. 按标题/章节切（适合技术文档）
2. 按代码块/注释边界切（适合 SDK 文档）
3. 按语义自然段落切（适合长文章）

**关键 metadata 字段：**
- `source_url` — 来源链接
- `title` — 章节标题
- `section_path` — 章节路径（"数据访问 > SQL 数据库 > 配置数据源 > HikariCP 连接池"）
- `version` — 文档版本号
- `section_level` — 标题层级
- `chunk_order` — 同章节内顺序
- `tags` — 标签
- `credibility` — 可信等级（official / community / deprecated）

**检索流程：先过滤 metadata 再搜语义。** 用户问 Spring Boot 3.2，先 filter(version == "3.2")，再搜向量语义。否则旧版本内容会污染结果。

### 七、Section Path（章节路径）

**核心：chunk 在文档里的"全路径地址"——让 LLM 和用户都知道这块内容来自整篇文章的哪个位置，而不是一个断章取义的碎片。**

作用：
1. **给 LLM 提供上下文语境** — 内容"maximum-pool-size=20"加上 section_path 才知道是 HikariCP 连接池配置
2. **让 LLM 给出精确引用** — 用户能直接去翻原文验证
3. **帮助理解 chunk 之间的关系** — 知道兄弟章节、父章节是谁

### 八、向量库工作原理

**准备阶段：** 文档切块 → 调用 Embedding API 转成向量 → 存入向量库（向量→原文的映射）
**查询阶段：** 用户问题 → 调用**同一个** Embedding 模型转成向量 → 进库算余弦相似度 → 返回 Top-K 最相关 chunk

关键点：文档和问题用同一个 Embedding 模型，两者映射到同一个向量空间，相似度才有意义。

### 九、Handbook 最小实践的理解

**"最小实践"三种类型：**

| 类型 | 章节 | 形式 |
|------|------|------|
| 概念类 | LLM / Prompt / Context | 伪代码 / 配置示例 / 文字说明 |
| 框架/工具类 | Agent / Frameworks / MCP | 可运行代码（Python/TS） |
| 操作类 | Fine-tuning / Inference | CLI 脚本 + API 调用 |

本质：**不是为了让你写代码跑起来，而是通过设计 Prompt 或设计方案，验证前面学的概念。**

### 十、LLM 章节最小实践：交易解释器（Tx Interpreter）

**练习：** 输入一笔交易哈希，让系统读取链上数据 + 合约 ABI，LLM 生成解释。

**考察的核心概念：**
- Context Engineering：把链上事实（tx hash、from、to、value、event）拼入 prompt
- 引用校验：标注"哪些信息来自链上数据 vs 模型推断"
- Reflection：输出"模型不确定的地方"
- 边界意识：链上事实 vs 模型推断分开

输出结构：用户发起什么动作、涉及资产和地址、链上事实 vs 模型推断、不确定的地方、签类似交易要检查什么。

### 十一、Agent 章节最小实践：DAO 提案研究 Agent

**练习：** 一个只能执行只读动作的 Agent——读取提案正文、检索论坛讨论、总结支持和反对理由、标记缺失信息、输出投票前检查清单。

**核心设计原则：不要让它直接投票。** 输出必须明确：
- 用了哪些来源
- 哪些结论证据不足
- 是否发现治理或资金风险
- 如果用户要投票，还需要人工检查什么

**权限升级版本：** 只有用户明确授权 + 经过投票交易 simulation 后，才允许生成投票交易草稿。

### 十二、Agent（智能体）章节核心概念

**核心定义：** Agent 不是"像人"的 AI，而是**被约束的执行循环**——工具、状态、权限、停止条件缺一不可。

- **Tool Use**：工具让 Agent "能做事"，但工具设计要明确 schema、权限、是否只读、是否有副作用
- **Planning**：把目标拆成步骤，但计划只是候选路线不是授权
- **State**：状态不能只藏在 prompt 历史里，要可查询、可恢复、可审计
- **Reflection**：自我检查提高质量，确定性检查才能承载风险
- **Multi-Agent**：多个 Agent 分工可能放大协调问题，不是减少复杂度

**AI × Web3 Agent 典型架构：**
用户目标 → Agent 读上下文生成计划 → 系统拆为只读/写入步骤 → 只读自动执行 → 写入进 policy 检查 → Simulation → 用户确认 → Wallet 执行 → 日志记录

**最危险的设计：** 模糊目标 + 广泛工具 + 长期记忆 + 大额资产权限

## 学习问答

**问：Context Engineering 到底在管什么？**

答：不是约束 LLM 怎么回答（那是 Prompt 的事），而是约束你给 LLM 看什么数据。就像一个拦截器：每次请求进来，你在数据到达 LLM 之前，决定放什么进去、删掉什么、摘要什么、按什么顺序排。Context Window 是 GPU 定的，Context Engineering 是你代码定的。

**问：为什么 Chunking 不能按字数切？**

答：按字数切会导致语义断裂（一句话被切成两半），或者产生"标题相似但内容不对"的噪声 chunk。好的 Chunking 要按文档结构切——遇到一个标题就切一刀，每个 chunk 语义完整，并且带上 section_path 防止断章取义。

**问：Section Path 在检索中有什么用？**

答：两个作用。一是让 LLM 知道这个 chunk 的上下文位置（"HikariCP 最大连接数" 属于 "数据访问 > 数据库配置" 大类）。二是让 LLM 在回答时给出精确引用路径，用户可以验证来源。

**问：LLM 章节的"交易解释器"最小实践，在考什么？**

答：考的是 Context Engineering（拼链上事实进 prompt）+ 引用校验（区分链上数据 vs 模型推断）+ Reflection（反思不确定的地方）+ 边界意识。不是写代码，是设计提示结构。

**问：Agent 的最小实践设计为什么故意限制只读？**

答：因为 Agent 最核心的设计问题是**权限边界**。只读版本让你先学会"给 Agent 划定范围"，不急着写。权限升级版本才引入 simulation 和用户授权，确保高风险操作有检查机制。跟昨天学的 EVM 确定性是呼应的——Simulation 可以在签名前预执行交易、看到结果。
