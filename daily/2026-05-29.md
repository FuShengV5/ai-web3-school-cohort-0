### 二、MCP（Model Context Protocol）

从 Handbook 拉取了 MCP 章节内容，MCP = AI 应用和外部工具的 **"USB 接口标准"**。

**四大核心概念：**

| 概念 | 说明 | 类比 |
|------|------|------|
| **Server** | 提供工具/资源的服务端 | USB 外设（打印机、U盘） |
| **Client** | 使用工具的 AI 应用端 | 操作系统（Windows/macOS） |
| **Tool Schema** | 工具的定义格式（参数+返回值） | USB 设备描述符 |
| **Permission** | 用户授权的访问控制 | 权限弹窗确认 |

**MCP vs Skill 的关系：**
- **MCP 管"工具怎么接"（协议层）** —— 定义了 AI 应用如何发现和调用外部工具
- **Skill 管"接了之后怎么用"（应用层）** —— 定义了用这些工具完成什么业务流程

用 Java 类比：MCP = JDBC（数据库连接协议），Skill = `OrderService` 类（业务流程编排）。两者不在一个抽象层上。

### 三、Skill（技能）概念

**Skill = 一个领域任务的"操作手册"，给 AI Agent 用。**

不是代码，不是工具，不是 prompt，而是三者的打包：

| 组成部分 | 作用 | 类比 |
|---------|------|------|
| **prompt** | 角色 + 行为准则 | 类的职责声明 |
| **plan** | 执行步骤/工作流 | 方法间的调用顺序 |
| **tools** | 允许使用的工具白名单 | 依赖注入的 bean |
| **rules** | 约束、坑点、边界 | 校验逻辑 + 异常处理 |

**存放位置：** `~/.hermes/skills/` 下，纯 markdown 文件（YAML frontmatter + Markdown body），按场景自动加载。

**创建方式：** 大部分是人写的，Agent 辅助沉淀——在日常对话中反复踩坑、调整流程后，Agent 将经验结构化写成 skill 文件。

**跨 CLI 可移植性讨论：**
- ✅ **可以移植的是知识本身** —— 流程、规则、坑点、用户偏好，用 markdown 写的内容任何 LLM 都能读懂
- ❌ **不能直接搬的是** —— 工具名（各 CLI 的工具集不同）、自动加载机制（Hermes 的 skill 匹配是独有的）
- 其他 CLI 有各自的等效机制：Claude Code 的 `CLAUDE.md`、Codex 的 `CODEX.md`、Cursor 的 `.cursorrules`
- **真正价值不在文件格式，而在里面装的知识**，知识可以跨 CLI，只是需要翻译格式

## 学习问答

**Q: 换了 CLI 或 LLM，skill 文件能直接复制过去用吗？**
A: 知识（流程、规则、偏好）可以，但工具名和自动加载机制不行。其他 CLI 有各自的等效配置文件（CLAUDE.md / CODEX.md / .cursorrules），需要把 skyll 里的内容翻译成对应的格式。

**Q: Skill 的跨 CLI 限制在哪？**
A: 两点：(1) 工具名不同 —— Hermes 的 `read_file`、`terminal` 在其他 CLI 里叫不同名字；(2) 自动加载机制不同 —— Hermes 会按场景自动匹配 skill，其他 CLI 需要手动配置或写在项目根目录的配置文件中。

### 四、回顾 LangChain vs LangGraph

**LangChain = 线性链**，适合确定性多步调用（如成绩环比：查当月→查上月→算环比），工厂流水线
**LangGraph = 带循环的图**，适合不确定性场景（写→编译→报错→改→再编译），用 LLM 循环自检保证数据可靠性

关键认知：循环的本质 = Agent 自我检查 → 发现错误 → 回头修正 → 直到正确。Spring AI 属于线性链，要实现循环需手动写 for 循环 + Reflection 检查 + 重试。

### 五、Vibe Coding（氛围编程）

**Vibe Coding 是方法论/场景，不是 AI 理论。** 它描述"人怎么用 AI 来写代码"——人凭"感觉"判断代码对不对，不逐行读代码。Karpathy 命名 "Vibe" 的用意：你跟代码的关系从"每一行的主人"变成"验收者，感觉差不多就行"。

**Handbook 中 Vibe Coding 章节的 8 个知识节点：**

| # | 节点 | 难度 | 本质 |
|---|------|------|------|
| 1 | Vibe Coding | 初级 | 场景/方法论 |
| 2 | Claude Code / Codex CLI | 初级 | 开箱即用的产品工具 |
| 3 | Model / API Config | 中级 | 自管基础设施（模型、key、成本、权限） |
| 4 | GitHub / gh | 中级 | 版本控制是人的最后防线 |
| 5 | CLI / Script | 中级 | 一次性脚本工具，注意 dry run |
| 6 | Repo Workflow | 高级 | AI 也要走正常工程流程，不能跳过 |
| 7 | 在 AI×Web3 的位置 | - | 链上代码风险高，不能只靠 Agent |
| 8 | 最小实践 | - | 完整工程闭环练习 |

**讨论重点：**

- **Vibe Coding ≠ 不审查**。简单任务凭感觉（真·Vibe），生产代码必须审慎
- **Node 2（Claude Code / Codex CLI）vs Node 3（Model / API Config）**：前者装上默认就能用，后者需要自己管模型、key、streaming、成本——Hermes 属于后者
- **Node 4（GitHub / gh）**：不是必须用 gh CLI，而是**审查习惯不能省**——你通过 IDEA 看 diff 再手动 push 也是同样效果
- **Node 5（CLI / Script）** = 你做的 JavaCliTool 这种一次性工具
- **Node 6（Repo Workflow）核心**：不要因为它是 AI 就跳过正常流程（开分支、看 diff、跑测试、review、merge）。把 AI 当成一个"干活快但偶尔犯错的新同事"
- **与你朋友说的"多 LLM 分工协作"区别**：朋友说的是多 Agent 分工干活（项目经理 AI + 前端 AI + 后端 AI + 测试 AI），Node 6 是说干完活后怎么合规上线。两者不冲突，可以串起来用
