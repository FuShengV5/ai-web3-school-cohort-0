### Hermes 微信接入架构

- Hermes 支持微信接入，适配器在 `gateway/platforms/weixin.py`
- **接入方式：** 通过腾讯 iLink Bot API，走 HTTP 长轮询，不是直接接入本机微信
- **架构链路：** <手机微信 ← 腾讯 iLink 服务器 ← Hermes（WSL2）>
- **实际效果：** 在微信里添加一个 iLink bot 身份（xxx@im.bot）作为联系人，跟它聊天 = 跟 Hermes 对话
- **关键限制：** iLink bot 是独立 bot 身份，不是接管现有微信号；群聊大概率不可用
- **配置步骤：** 安装 aiohttp + cryptography → `hermes gateway setup` 扫码登录 → `hermes gateway` 启动

### Hermes 框架定位

- Hermes 不是一个单纯的对话工具，而是一个 Agent 框架（tools / skills / memory / cron / gateway 等完整能力）

### TC 老师课程：Web2 vs Web3 支付模型

#### Web2 支付模型（银行转账模型）

三个对象：用户 → 支付服务（TC） → 银行机构。关键理解：

- **无真实资金流动**：全程只是银行数据库里的数字变更（UPDATE accounts SET balance = balance - 20）
- **信任银行权威**：银行是中心化信任核心，可单方面冻结、回滚、暂停服务
- **安全检查点**：服务间 API Key 认证、用户支付密码/MFA、数据篡改和伪造认证防范
- **钱包本质**：Web2 的"钱包"只是银行里的记账数据，用户没有真正的控制权

类比：A给B转账，本质是A告诉银行"扣我的钱加给B"，银行签字改账本。

#### Web3 支付模型（去中心化）

核心替换：Bank Institution → Block Chain。关键理解：

- **区块链定位**：另一种形式的银行机构，Layer1 / Layer2 可理解为不同的银行体系
- **信任模型变化**：从信任权威机构 → 去中心化信任（数学 + 密码学 + 共识机制）
- **区块链本质**：不仅是一个数据库，还是一个全球共享的、确定性的状态机
- **钱包本质**：不是存储资产的容器，而是管理私钥（开启资产大门的钥匙）的工具

类比：A到B面对面交易——A直接用私钥（=当面把钱塞到B手里），全网见证，账本自动更新。

#### Web3 交易生命周期

**三步走：构造（Construct）→ 签名（Sign）→ 广播（Broadcast）**

1. **构造**：定义交易意图，封装关键参数：
   - **Nonce**：账户交易序号（从0递增），防止重放攻击，确保交易顺序
   - **Gas**：手续费，Gas Fee = Gas Count × Gas Price
   - **Data**：智能合约的指令集，定义业务逻辑和参数

2. **签名**：用私钥赋予交易法律与技术效力，确保所有权不可篡改。签名后任何人都可根据公钥验证：这笔交易确实是你签的，且未被篡改

3. **广播**：提交至网络节点，进入 Mempool 等待打包。节点验证：签名有效性、Nonce 一致性、余额是否充足。一旦区块被确认（如以太坊 12 个区块），交易不可逆

#### 对比总结

| 维度 | Web2 | Web3 |
|------|------|------|
| 信任对象 | 银行权威 | 数学 + 共识 |
| 资金流转 | 数据库字段变更 | 链上状态转移 |
| 可逆性 | 可回滚、可冲正 | 确认后不可逆 |
| 容错空间 | 较大（可修复） | 为零（漏洞即归零） |
| 安全要求 | 高并发 + 可用性 | 极度的工程严谨性 |

### 核心结论（TC 老师总结）

- AI 没有降低系统复杂度，它只是加速了代码堆砌
- Web3 不是新世界，而是对分布式工程提出了更严苛的要求
- 安全即理解力——无法解释系统行为就无法保证资产安全
- AI 让编码更简单，但让理解系统更重要

### 架构师能力模型（三位一体）

- **架构能力**：设计高可用、高安全的分布式系统
- **Debug 能力**：深入底层协议，解释每一个逻辑背后的技术原因
- **基础能力**：对底层共识机制、密码学原理与链上状态模型的深刻理解
